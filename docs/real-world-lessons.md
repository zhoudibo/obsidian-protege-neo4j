# 实战踩坑全记录

> 这份文档区分**设计意图**和**已验证结论**。凡是没跑过的，明确写"未验证"。
> 记录真实的数字和真实的报错，不写"业内最佳实践"。

## 一、这套架构解决的真问题

**原始症状**：Obsidian 里明明写过，为什么找一条相关经验还要翻半天？

**根因**：文件、标签和 `[[链接]]` 分散着，没法一次问清"这张卡归哪个主题、它又指向哪些卡"。

**不是**笔记太少，**也不是**搜索不够强。是**数据形态**问题——纯文本结构撑不住关系查询。

## 二、三层划分的真实边界

```
Obsidian Vault  ──ETL──▶  CSV  ──import──▶  Neo4j
     事实源                 传输层             查询投影
```

**关键决策**：把 CSV 作为**独立的一层**，而不是从 Obsidian 直连 Neo4j。

这样做的代价是多一步。收益是：
- CSV 可 diff（这次同步到底改了什么，一眼看清）
- CSV 可审计（灌库前能人工核对表头和抽样行）
- CSV 可重放（导错了，换个空库重灌即可，不用重跑 ETL）
- ETL 阶段可以做脱敏，Neo4j 里永远不出现原始敏感内容

## 四、五个真实踩过的坑

### 坑 1：`:ID` 不是属性

**现象**：首灌成功，但日更同步后节点数暴涨，或旧节点被错误回收。

**根因**：Neo4j 离线导入的 `:ID` 列只用于**导入时**匹配关系端点，它**不会**存成节点属性。而日更脚本用的是 `MERGE (n:KBNode {id: $id})`——节点上没有 `id` 属性，MERGE 永远匹配不到。

**修复**：`prepare_import.py` 保留 `:ID`，**额外写入普通 `id` 属性**，并给所有节点加 `KBNode` 标签。

**验收**："同一输入跑两次，节点数不增加。"

**教训**：这类问题在首灌时完全看不出来。首灌只验规模，日更才验幂等。**两个环节都要验。**

### 坑 2：标签被误删

**现象**：早期增量实现把"本轮没扫描到的节点"直接删掉，**差点把未变更但仍被引用的标签一起清掉**。

**根因**：把"文件"的所有权模型套用到了"标签"身上。标签不属于任何文件——三个文件可以打同一个标签，删一个文件不该动标签。

**修复**：区分归属。

```
文件/目录 → 对照 vault 现存 ID（哈希基线），消失才删
标签      → 只回收无入边的孤儿标签
源系统    → 永不自动删
```

**教训**：图数据库里"删除"的默认答案是"不删"。**要证明一个节点该被删，比证明它该留着难得多。**

### 坑 3：标题当 ID 导致同名合并

**现象**：不同目录的 `00_索引.md` 在图里变成了同一个节点。

**根因**：用标题做 ID。而每个目录都有 `00_索引.md`——标题必然撞。

**修复**：ID 用 vault 内相对路径。

**代价**：改名/移动会改 ID。同步要按"旧 ID 删除 + 新 ID 建立"处理，不能假装没有影响。

**衍生问题**：同名链接产生歧义。此时**不能猜**——脚本应该报歧义，然后让人去源笔记里改用路径式链接 `[[dir/名称]]`。

### 坑 4：输出目录在 vault 内

**现象**：图里出现 `nodes.csv` 这种奇怪节点，而且节点数每跑一次涨一截。

**根因**：ETL 输出目录在 vault 内部，下次扫描把产物当笔记读了。

**修复**：硬编码检查，不靠自觉。

```python
if out == vault or vault in out.parents:
    raise ValueError('output directory must be OUTSIDE the vault')
```

**教训**：凡是"扫描目录"的脚本，都必须有"输出目录不能被扫描"的硬约束。**靠文档提醒早晚会出事。**

### 坑 5：把"备份存在"当成"能恢复"

**现象**：备份文件都在、校验都过，但真要恢复时发现根本恢复不了。

**具体缺口**：
- **Git bundle 不含未跟踪附件**——bundle 只含 Git 已跟踪内容
- **同机 `.backup` 不抵御整盘损坏**
- **Community 版 `neo4j-admin database dump` 要求数据库离线**——不能拿在线 dump 当已跑通

**修复**：把验证分成两级，结论分开写。

| 层级 | 动作 | 合格证据 |
|---|---|---|
| A 级：导出完整性 | 读 JSON，核节点 ID、关系两端、记录数；核 bundle 可打开 | 证明备份文件结构可信 |
| B 级：隔离恢复 | 空库/另一台机器导入；跑节点/关系计数 + 3 条固定查询；抽查原卡 | 才能写"灾难恢复成功" |

**教训**："文件存在"和"能恢复"之间隔着一整套演练。这道坎不迈过去，备份就只是心理安慰。

## 五、增量的四步验收（必须做）

```text
① --dry-run：先看预计写入、预计删除；删除数异常就停。
② 新增 demo_vault/经营笔记/临时卡.md，内含 [[商品资料]]，同步后查临时节点和 LINKS_TO。
③ 移走临时卡，再同步；确认临时节点被清理、商品资料仍在。
④ 对同一状态再跑一次；总数不应继续涨，重复边不应出现。
```

**每一步都要记前后计数。** 没有前后计数的验收等于没验收。

### 停手线的来源

早期钩子没有停手线。后来加的规则：

> 如果 vault 扫描量突然远低于上次，或预计删除数量超过阈值，就**停止删除并报警**。

**这条是复盘给读者的增强建议，不是原工程已验证能力。** 本仓库把它实现成了默认行为（`kb_sync_plan.py` 的 `SAFETY: STOP` + 退出码 1），但要清楚：**原工程当时尚未实现。**

## 六、本体设计的真实教训

### Protégé 是 GUI，验证必须落在文件上

原工程用 `kb_build_ontology.py` 生成实例、`kb_finalize_ontology.py` 定稿，Protégé 用来检查类和关系是否符合业务语言。

**但没法把 Protégé 窗口截图当证据**——更没法从截图断言"有 13 个类"。

所以本仓库提供 `owl_check.py`：从保存的 `.owl`/`.ttl` 里直接读出类数、对象属性数、domain/range、inverseOf，并给出告警。

**模型在 GUI 里做，验证在文件上做。** 这条能直接写进报告。

### 关系方向必须写进 domain/range

灌完 4 万节点才发现方向反了 = 全量返工。

**写 domain/range 的时候顺手定方向**。然后用 `owl_check.py` 核一遍，报告里直接贴输出。

### 语义要能用业务语言读

类名和关系名应该是业务方能读懂的：

```
ServiceWorkOrder（服务工单）
CONCERNS → ProductModel
TAGGED_WITH → Tag
```

不是 `SWO_001`、`REL_17`。

### SHACL 约束要写 message

```turtle
sh:message "BOM明细必须且只能指向一个物料。"@zh-CN
```

用业务语言写 message。人看不懂的校验规则等于没有。

## 七、治理脚本自己会腐烂

**真实事故**：某个旧版月度图健康脚本仍在读已迁走的 `password` 配置项，当前配置已改为 `credentials_file`，**本轮实际执行直接报错**：

```
[ERROR] 无法连接 Neo4j (...): 'password'
```

**这不是文档问题，是代码问题。**

安全治理必须包含一条：**治理脚本本身能否跑通**。修完还要重跑，不能改完代码就宣布通过。

同理，上一版月度报告有 **35 个未提交改动的 WARN**——就该写 35 个 WARN，不是"全绿"。

## 八、审计输出的纪律

**错误做法**：
```
[凭据扫描] 密码是 SuperSecret123
```

**正确做法**：
```
[凭据扫描] 命中 2 处，明文未记录
    位置：./config/legacy.yml:14
    位置：./notes/2026-10-27.md:88
```

秘密留在受保护凭据文件（权限 600），报告里只出现位置和条数。

## 九、还没做完的事

诚实列出来，因为**这些是本仓库同样没覆盖的**：

- ❌ **隔离库真正恢复演练** —— 本仓库只提供 A 级校验脚本，B 级需要真实 Neo4j 实例
- ❌ **异盘 / 加密异地副本** —— 同机备份不抵御整盘损坏
- ❌ **附件全覆盖备份** —— Git bundle 不含未跟踪附件
- ❌ **月度体检脚本自身修复** —— 旧 `password` 配置项问题需在原工程修复
- ❌ **真实整库的隐私过滤** —— 本仓库的 `--exclude` 是机制，规则要按库自己定

**未跑通的步骤标"未验证"，不写"已上线"或"恢复成功"。** 这条铁律能挡掉绝大多数复盘里的注水。
